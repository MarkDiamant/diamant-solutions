- **Vercel project domain** `*.diamantsolutions.co.uk` is **verified: true** in the project-domain record, but `get_domain_config` still reports **misconfigured: true** with **no conflicting records**. These are different status checks; project ownership verification does not establish production TLS readiness.
- **Authoritative GoDaddy nameservers:** `ns03.domaincontrol.com` and `ns04.domaincontrol.com`. Both return authoritative `NOERROR`, CNAME `cname.vercel-dns.com.`, TTL **3600** for a randomly chosen unused subdomain. Public resolvers **1.1.1.1** and **8.8.8.8** return the same CNAME. **DNS propagation is complete at all four checked servers**; do not request the user to add the CNAME again.
- A fresh random wildcard hostname resolves to Vercel IPs, but an HTTPS probe returned **TLS handshake unexpected EOF**. In contrast, `https://bms.diamantsolutions.co.uk/` returned HTTP **307** with Vercel headers. Wildcard **HTTPS/TLS issuance or edge activation remains unverified**, so new customer subdomains are **not launch-accepted** despite valid DNS. Vercel's team-scoped certificate inventory contains **no** certificate for `*.diamantsolutions.co.uk`. A team-scoped attempt to issue one returned **HTTP 449 `dns_pretest_cns_not_using_vercel_ns_error`**, because the authoritative nameservers are GoDaddy, not Vercel. Therefore the wildcard CNAME **does propagate correctly but is insufficient for Vercel-managed wildcard TLS issuance** in this setup. A deliberate DNS delegation/managed-certificate solution is required; do not change the apex nameservers without planning migration of every existing DNS record (mail and other sites), and do not alter tenant routing.
