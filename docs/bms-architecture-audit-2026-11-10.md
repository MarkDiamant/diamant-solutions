# BMS architectural audit: 2026-11-10 (evidence-based, incomplete)

## Observed deployment architecture
- Canonical source: `MarkDiamant/diamant-solutions/business-software-core/`. The repository's `AGENTS.md` explicitly requires a single shared BMS core, versioned package consumption by M&J, and tenant-scoped branding/data. It contains contradictory historical migration notes about copied files, superseded by the 2026-10-20 immutable-package note; current M&J source inspection remains necessary to verify the latter.
- Standalone `bms.diamantsolutions.co.uk` and embedded `diamantsolutions.co.uk/software` are served from Vercel project `diamant-solutions` (`prj_NeXx3jHox2oyr14nzUAxogtVqjDp`). Its production deployment `dpl_CDk3zWjEenhrvYCK5xtbPqw2hFjk` is `READY` on `main` commit `80d04da85`. The canonical core on `main` is **1.0.43**. A package version in source is not proof that all live route bundles are on that version; validate rendered bundles and deployment manifest.
- `app/bms-runtime/page.tsx` imports `CrmDashboardV5`; its wrapper re-exports the canonical `business-software-core` implementation. Demo parity script checks shared UI component wiring but the demo API uses **separate fictional handlers**. This is an intentional data-isolation boundary, not necessarily a UI fork; actual functional parity needs browser tests.
- M&J Vercel project `mjmetal` (`prj_oOg8V3r5UALCtUPvfq4LL1a9jjBS`) is a separate deployment. Production `dpl_HqXAWgyZ4aQUcpwJdM1geeV5dvf8` is `READY` on `MarkDiamant/mjmetal` commit `de264fff`, whose Git commit message explicitly states **“Automatically consume shared BMS core v1.0.38”**. Seven preceding production deployments consumed v1.0.31 through v1.0.37. Thus an automatic update mechanism **previously existed**, but it has not delivered v1.0.39–v1.0.43 to current M&J production. Why it stopped is **not established**; no GitHub source access to `MarkDiamant/mjmetal` was available through the connected GitHub integration, so workflow runs, lockfile, version pin and package source cannot be independently audited. Do not infer it is a maintained fork or that all missing releases were published.
- Preview `bms-acceptance.diamantsolutions.co.uk` is separate from both production projects. Shared core `1.0.44` exists only on the acceptance branch and is **not released**.

## Critical unresolved findings
1. **Deployment version skew confirmed** between M&J v1.0.38 and canonical main v1.0.43. The isolated branch v1.0.44 has not reached either production. This is a release-distribution failure, not proof of divergent source implementations.
2. **Other tenant inventory unknown.** The Vercel project list shows no additional dedicated BMS projects beyond `diamant-solutions` and `mjmetal`; multiple logical tenants may run in the shared project. Their tenant registry, host mappings, deployed bundle versions and authentication must be audited before claiming universal coverage.
3. **Demo is a shared UI with separate API/data behavior.** API parity and isolation cannot be assumed from component imports alone.
4. **No authenticated browser acceptance** has been completed; Preview build success and source assertions are insufficient.

## Release architecture correction
Use one immutable canonical shared-core package with a **single manifest listing every deployment target**, explicit package version and integrity, pinned dependency and lockfile, a fail-closed parity gate and authenticated tests on each target. Stage Preview builds before requesting approval. Production promotion requires explicit user approval and safe rollback to previously recorded immutable packages. The new read-only `scripts/bms-deployment-parity-gate.cjs` rejects stale or unverified tenants and missing acceptance evidence. It does **not** yet discover the full tenant registry or upgrade inaccessible M&J source; those are mandatory blockers.

## Data protection
Never overwrite tenant branding/settings or customer data during package updates. Maintain RLS, tenant-scoped unique job references, reversible application rollback, verified migration compatibility, and backup/restore procedures. No production migration or deployment authorised.
